LEXER TOKEN GRAMMAR

Before automata state evaluation occurs, the raw ASCII telemetry stream is tokenized by an in-line lexical scanner into a compact five-symbol alphabet Σ = {LEVEL, IP, USER, STATUS, OTHER}. The scanner relies entirely on C++14 std::string_view slices to achieve zero dynamic memory allocations.

TABLE 3: FORMAL TOKEN RECOGNITION GRAMMAR & EXTRACTION RULES
Token Symbol (σ) Regular Expression Pattern Sample Match Payload Semantic Validation Rule
LEVEL [A-Z]{3,8} INFO, WARN, ERROR Must match standard syslog RFC-5424 severity enum.
IP [0-9]{1,3}(\.[0-9]{1,3}){3} 192.168.1.105, 10.0.4.12 Strict octet validation (0 ≤ octet ≤ 255).
USER [a-zA-Z0-9_.@-]{1,32} root, admin, db_svc Must not contain SQL or shell meta-characters (', ", ;, --).
STATUS [0-9]{3} 200, 401, 403, 500 HTTP status code range (100 ≤ code ≤ 599).
OTHER [^\s]+ <script>, UNION SELECT Unmatched residual payload tokens triggering error state qE.

Zero-Allocation Memory Architecture

Conventional log parsers allocate heap memory for each parsed substring, incurring severe garbage-collection pauses and heap fragmentation under 100k EPS loads. Our C++14 implementation utilizes non-owning std::string_view pointers over pre-allocated ring-buffer pages, achieving 0 heap allocations during normal operation.

Deterministic Scanner Complexity

The lexical scanner executes in strict single-pass linear time: T(N) ≤ c × N, where c is a small constant (approx 14 CPU instructions per character). Even malformed input payloads with millions of consecutive punctuation marks complete in deterministic time without stalling worker threads.
